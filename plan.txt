  # Simple End-to-End GST RAG Application

  ## 1. Goal

  Build an interview-ready GST assistant that demonstrates the complete RAG lifecycle:

  ```text
  Admin uploads documents
    → documents are parsed and chunked
    → chunks are embedded and stored
    → user asks a question
    → backend checks the user's plan
    → only permitted documents are searched
    → Gemini generates a cited answer
    → Langfuse records the complete trace
    → risky answers are sent for admin review
    → a scheduled worker checks for new GST notifications
  ```

  The application will be simple enough to understand and explain, but complete enough to demonstrate production thinking.

  ## 2. Technology stack

  | Area | Technology | Purpose |
  |---|---|---|
  | Frontend | Next.js + TypeScript | Chat, login, admin upload, review page |
  | Backend | FastAPI + Python | Business logic and RAG pipeline |
  | Authentication | Supabase Auth | Login and user identity |
  | Database | Supabase PostgreSQL | Users, documents, chunks, answers |
  | File storage | Supabase Storage | Original PDF files |
  | Vector search | Supabase `pgvector` | Store and search embeddings |
  | PDF parsing | Docling | Extract text, headings, tables, and pages |
  | Embeddings | Jina embeddings | Convert chunks/questions into vectors |
  | LLM | Gemini | Classification and answer generation |
  | Observability | Langfuse | LLM traces, retrieval debugging, latency, cost |
  | Notification worker | Python script | Check official CBIC updates |

  Supabase is used instead of AWS and Pinecone because one platform can provide authentication, storage, PostgreSQL, and vector search through `pgvector`.
  citehttps://supabase.com/docs/guides/database/extensions/pgvector

  Langfuse will trace the RAG pipeline and show what happened inside each request. citehttps://langfuse.com/docs

  ## 3. User roles and access

  There are three roles:

  ```text
  Admin
  Plus
  Pro
  ```

  The source access model is:

  | Role | ICAI books | Private books | GST notifications |
  |---|---:|---:|---:|
  | Admin | Yes | Yes | Yes |
  | Plus | Yes | No | Yes |
  | Pro | Yes | Yes | Yes |

  There are only three document types:

  ```text
  icai_book
  private_book
  notification
  ```

  There is no separate “opinions” type. Everything inside the private book—including explanations, examples, analysis, or opinions—is treated as
  `private_book` and is available only to Pro users.

  The frontend cannot decide access. The backend calculates it:

  ```python
  if user.role == "plus":
      allowed_sources = ["icai_book", "notification"]

  elif user.role == "pro":
      allowed_sources = [
          "icai_book",
          "private_book",
          "notification",
      ]

  elif user.role == "admin":
      allowed_sources = [
          "icai_book",
          "private_book",
          "notification",
      ]
  ```

  This is important for the interview:

  > “The UI can hide private content, but the real security boundary is implemented in the backend before retrieval.”

  ## 5. Admin upload flow

  ### Step 1: Admin selects a PDF

  The admin selects:

  ```text
  PDF file
  title
  source type
  publication date
  effective date
  document number
  ```

  Example:

  ```text
  File: notification_15_2025.pdf
  Source type: notification
  Document number: 15/2025-Central Tax
  Publication date: 2025-06-10
  Effective date: 2025-07-01
  ```

  ### Step 2: Backend verifies the admin

  The request reaches FastAPI.

  FastAPI checks:

  ```text
  Is the user logged in?
  Does the user exist?
  Does the user have admin role?
  Is the file a PDF?
  Is the file size acceptable?
  ```

  If the user is not an admin, the upload is rejected.

  ### Step 3: PDF is stored

  The original PDF is stored in Supabase Storage.

  The database stores:

  ```text
  document_id
  file path
  source type
  file checksum
  uploading admin
  upload time
  processing status
  ```

  Initial status:

  ```text
  processing
  ```

  The original PDF is preserved so that citations can always refer back to the exact uploaded document.

  ### Step 4: Docling parses the PDF

  Docling converts the PDF into a structured representation:

  ```text
  document
    ├── page 1
    │   ├── heading
    │   ├── paragraph
    │   └── table
    ├── page 2
    │   ├── heading
    │   └── paragraph
    └── page 3
        └── example
  ```

  The parser should preserve:

  - Page number.
  - Heading hierarchy.
  - Paragraph boundaries.
  - Tables.
  - Lists.
  - Examples.
  - Footnotes where possible.

  The result is saved as an intermediate JSON or Markdown representation for debugging.

  ### Step 5: Document is cleaned

  The pipeline removes or normalizes:

  - Repeated headers.
  - Repeated footers.
  - Page numbers that are not meaningful content.
  - Broken whitespace.
  - Duplicate lines.
  - OCR artifacts where possible.

  It must not remove:

  - Definitions.
  - Conditions.
  - Exceptions.
  - Effective dates.
  - Notification numbers.
  - Section numbers.
  - Table values.
  - Important footnotes.

  ### Step 6: Document is chunked

  The initial chunking strategy is section-aware.

  ```text
  PDF
    → document sections
    → paragraphs and tables
    → semantic chunks
  ```

  The chunker should first use headings and sections rather than cutting the PDF at arbitrary character counts.

  For example:

  ```text
  Chapter 5
    Input Tax Credit
      5.1 Eligibility
      5.2 Conditions
      5.3 Exceptions
      5.4 Examples
  ```

  A chunk should preferably contain a complete concept.

  Good chunk:

  ```text
  Section: Conditions for claiming input tax credit

  A registered person may claim input tax credit when...
  The following conditions must be satisfied...
  However, this does not apply when...
  ```

  Bad chunk:

  ```text
  A registered person may claim input tax
  ```

  The rest of the condition is missing.

  Initial chunking defaults:

  ```text
  Target size: approximately 500–800 tokens
  Overlap: approximately 80–120 tokens
  Split by: headings, paragraphs, and sentences
  Keep together: definitions, conditions, exceptions, tables, examples
  ```

  Each chunk stores parent context:

  ```text
  chunk_id
  document_id
  source_type
  page_number
  chapter
  section_path
  section_title
  content
  embedding
  publication_date
  effective_date
  ```

  This chunking strategy is a starting point. The exact rules can be refined later when you provide more ingestion and document-format requirements.

  ### Step 7: Embeddings are created

  Each final chunk is sent to Jina embeddings.

  ```text
  chunk text
    → Jina embedding model
    → vector of numbers
  ```

  The embedding represents the meaning of the chunk.

  The vector and original text are stored together in Supabase:

  ```text
  content
  embedding
  page_number
  document_id
  source_type
  metadata
  ```

  ### Step 8: Document becomes active

  After successful parsing, chunking, and embedding:

  ```text
  processing → active
  ```

  If anything fails:

  ```text
  processing → failed
  ```

  The admin can see:

  ```text
  document name
  source type
  number of chunks
  processing status
  error message
  ```

  ## 6. User question flow

  ### Step 1: User logs in

  Supabase Auth identifies the user.

  The backend obtains:

  ```text
  user_id
  role
  ```

  The frontend may show:

  ```text
  Current plan: Plus
  ```

  But the backend remains the source of truth.

  ### Step 2: User submits a question

  Example:

  ```text
  What is the time limit for claiming input tax credit?
  ```

  The request goes to:

  ```text
  POST /api/chat
  ```

  ### Step 3: Langfuse trace begins

  FastAPI creates a Langfuse trace:

  ```text
  trace: chat_request
  ```

  The trace records:

  ```text
  request ID
  user role
  question category
  retrieval time
  model time
  answer status
  ```

  Sensitive document text should be masked or omitted from Langfuse when using real private documents.

  ### Step 4: Backend checks access

  For a Plus user:

  ```text
  Allowed:
    icai_book
    notification

  Blocked:
    private_book
  ```

  For a Pro user:

  ```text
  Allowed:
    icai_book
    private_book
    notification
  ```

  This source list is created by the backend. The user cannot modify it.

  ### Step 5: Gemini classifies the question

  Gemini performs a small classification task:

  ```text
  definition
  rate
  deadline
  eligibility
  notification_update
  comparison
  unclear
  off_topic
  ```

  Example:

  ```text
  Question: What is the time limit for claiming ITC?
  Type: deadline
  ```

  If the question is too unclear:

  ```text
  Could you clarify whether you mean ITC for goods, services, or imports?
  ```

  The system does not perform retrieval until the question is sufficiently clear.

  ### Step 6: Query embedding is created

  The final question is sent to Jina:

  ```text
  question
    → embedding vector
  ```

  ### Step 7: Supabase performs filtered vector search

  The SQL search function receives:

  ```text
  query_embedding
  allowed_source_types
  number_of_results
  ```

  For Plus:

  ```text
  match source_type in ('icai_book', 'notification')
  ```

  For Pro:

  ```text
  match source_type in (
    'icai_book',
    'private_book',
    'notification'
  )
  ```

  The database returns the closest chunks:

  ```text
  chunk content
  document title
  source type
  page number
  similarity score
  effective date
  ```

  ### Step 8: Evidence is prepared

  The backend selects the best five chunks and formats them for Gemini:

  ```text
  Source 1:
    Document: ICAI GST Book
    Page: 42
    Section: Input Tax Credit
    Content: ...

  Source 2:
    Document: Notification 15/2025-Central Tax
    Page: 2
    Effective date: 2025-07-01
    Content: ...
  ```

  ### Step 9: Gemini generates a grounded answer

  Gemini receives:

  ```text
  system instructions
  user question
  retrieved evidence
  citation metadata
  ```

  The prompt requires Gemini to:

  - Use only the retrieved evidence.
  - Avoid unsupported claims.
  - Cite document and page.
  - Mention notification updates.
  - State when evidence is insufficient.
  - Never reveal unavailable source content.

  ### Step 10: Citation validation runs

  The backend checks:

  ```text
  Does every citation refer to a retrieved chunk?
  Does the document exist?
  Does the page number exist?
  Does the answer contain at least one source?
  ```

  If validation fails:

  ```text
  status = review_required
  ```

  If no reliable evidence was retrieved:

  ```text
  status = refused
  ```

  The system responds:

  ```text
  I could not find enough reliable source material to answer this confidently.
  ```

  ### Step 11: Risk check runs

  The answer is flagged for review if:

  - It concerns a penalty.
  - It concerns a deadline.
  - It gives a compliance action.
  - Book and notification content conflict.
  - Citations are missing.
  - Similarity scores are low.
  - The answer relies on private-book content.
  - The system cannot determine which notification is current.

  ### Step 12: User receives a result

  Approved answer:

  ```text
  Answer:
  ...

  Sources:
  - ICAI GST Book, page 42
  - Notification 15/2025-Central Tax, page 2
  ```

  Review-required answer:

  ```text
  This answer requires admin review before it can be shown.
  ```

  Refused answer:

  ```text
  I could not find enough reliable source material to answer this question.
  ```

  ## 7. Notification worker flow

  The notification worker is intentionally simple.

  ```text
  Scheduled Python script
    → checks official CBIC source
    → finds notification links
    → compares with known documents
    → downloads new documents
    → sends them through the same ingestion pipeline
  ```

  The official CBIC Tax Information portal should be the primary source for GST notifications. citehttps://taxinformation.cbic.gov.in/

  Example:

  ```text
  worker starts
    → fetch official notification listing
    → notification 15/2025 already exists
    → notification 16/2025 is new
    → download notification 16/2025
    → save to Supabase Storage
    → parse with Docling
    → chunk
    → embed
    → store in pgvector
    → mark active
  ```

  The worker should record:

  ```text
  last run time
  number of documents found
  number of new documents
  number of failed documents
  error message
  ```

  Initially, the worker can run manually:

  ```bash
  python worker/check_notifications.py
  ```

  Later, run it periodically using a simple scheduled job.

  ## 8. Notification and book comparison

  The first version should not build a complex legal reasoning engine.

  It should perform basic comparison:

  ```text
  book publication date
  notification publication date
  notification effective date
  notification number
  amends/supersedes text
  ```

  If the user asks:

  ```text
  What is the current GST rate for this item?
  ```

  The system should retrieve both:

  ```text
  older book explanation
  newer notification
  ```

  The answer should say:

  ```text
  The ICAI book describes the earlier position.
  The later notification changes or clarifies the applicable rule.
  The notification is effective from [date].
  ```

  If the system cannot confidently determine the effect:

  ```text
  status = review_required
  ```

  ## 9. Langfuse observability

  Every chat request creates one Langfuse trace:

  ```text
  chat_request
    ├── authenticate_user
    ├── classify_question
    ├── create_query_embedding
    ├── retrieve_chunks
    ├── generate_answer
    ├── validate_citations
    └── final_result
  ```

  Every ingestion request creates another trace:

  ```text
  document_ingestion
    ├── download_or_upload_file
    ├── parse_with_docling
    ├── clean_document
    ├── create_chunks
    ├── create_embeddings
    └── store_vectors
  ```

  Track:

  - End-to-end latency.
  - Retrieval latency.
  - Number of retrieved chunks.
  - Similarity scores.
  - Gemini latency.
  - Token usage.
  - Estimated model cost.
  - Citation validation result.
  - Review-required count.
  - Refusal count.
  - Ingestion failures.
  - Chunk count per document.
  - Notification worker success/failure.

  Langfuse lets you inspect the actual internal flow instead of only seeing the final answer.

  The project will not add Phoenix, Datadog, Grafana, Prometheus, or a separate distributed tracing platform.

  ## 10. Guardrails

  ### Access guardrails

  - Authentication required.
  - Admin-only uploads.
  - Backend-controlled Plus/Pro permissions.
  - Source filtering before vector search.
  - No client-supplied allowed-source list.
  - No private-book retrieval for Plus users.

  ### RAG guardrails

  - Uploaded documents are treated as data, not instructions.
  - Retrieved chunks are treated as evidence, not executable prompts.
  - Gemini must answer only from retrieved context.
  - Weak retrieval results trigger refusal.
  - All important claims require citations.

  ### Output guardrails

  - Verify citation document and page.
  - Flag contradictory sources.
  - Flag high-risk questions.
  - Prevent unapproved drafts from reaching users.
  - Show an informational-use disclaimer.

  External moderation systems such as NeMo Guardrails and Llama Guard are intentionally excluded from the first version. They can be added later after the
  basic flow is working.

  ## 16. Interview explanation

  The complete explanation should be:

  > “An admin uploads GST PDFs and labels them as ICAI books, private books, or notifications. Docling extracts the document structure and page
  information. I chunk the content by sections while keeping definitions, exceptions, and tables together. Jina converts each chunk into an embedding,
  which I store with the text and citation metadata in Supabase using pgvector.
  >
  > When a user asks a question, the backend reads the user’s role and calculates the permitted source types. Plus users can search ICAI books and
  notifications, while Pro users can also search private books. This permission is enforced before vector search, not just in the UI. The retrieved chunks
  are sent to Gemini with instructions to answer only from the evidence and include citations. Citation and risk checks decide whether the answer can be
  shown or requires admin review. Langfuse traces every step so I can inspect latency, retrieval quality, token usage, and failures. A scheduled Python
  worker checks official CBIC notifications and sends new documents through the same ingestion pipeline
